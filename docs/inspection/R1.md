# Echo — Implementation & Release-Readiness Audit

**Audit type:** Read-only implementation and release audit  
**Repository:** `/home/guts/P2/KBA` (`mvp_01`, commit `1cc899c`)  
**Date:** 27 Oct 2026  
**Verdict:** **Not release-ready.** The UI is polished and the backend pipeline works in isolation, but the shipped app cannot reach the backend on a real device, the client API is unauthenticated, and several delete/consent promises are not implemented. Four P0, nine P1, twelve P2, and four P3 findings are listed below. No fixes were implemented.

---

## 1. Executive summary

The product is a Flutter voice/text capture app backed by a FastAPI + SQLite service with local Whisper/faster-whisper transcription, heuristic or optional OpenAI extraction, fastembed semantic recall, and an admin dashboard.

### What is genuinely working

- Clean hexagonal backend structure with domain/application/adapters separated.
- `flutter analyze` is clean; the existing mobile and server test suites pass.
- Release APK builds successfully.
- The backend `upload → decode → transcribe → extract → embed → semantic search` path was exercised end-to-end with synthetic speech in a temporary environment.
- Audio is not retained when `consent_given=false` on the tested success/failure paths.
- The main UI flows (capture sheet, library list, recall, detail, settings) are visually complete and navigable in widget tests.

### What blocks release

1. **The installed app cannot reach the backend.** The default server URL is `http://127.0.0.1:8000`, and Settings has no field to change it. On a physical phone, localhost is the phone itself; on an emulator it is the emulator. Voice capture therefore always ends in `failed`, and text notes silently fail to sync. The AI fallback cannot help because the API key also has no UI.
2. **Every client API is unauthenticated.** Anyone who can reach the port can read, create, and delete all knowledge, upload audio, and trigger consent purges. The admin token has a hardcoded default, and the README instructs binding to `0.0.0.0`.
3. **The upload endpoint allows arbitrary file writes outside the upload directory** through an unsanitised `capture_id` filename, and reads the entire body into memory with no size cap. Confirmed with a live request.
4. **The release APK is debug-signed and still carries template identity** (`com.example.mobile`, label `mobile`), so it cannot be published.

### What is most dangerous after those

- Opening a note while AI processing finishes can overwrite the new AI title/summary with stale empty controllers on Save.
- Deleting a note removes only the local row and the server knowledge item; the server capture row, job rows, evaluation rows, and retained audio remain. The dialog explicitly promises audio, transcript, and ideas are removed.
- The local SQLite `onUpgrade` drops the entire `notes` table. The next schema bump wipes all user notes.
- The knowledge graph places nodes outside its fixed 500×500 canvas; isolated nodes reach `y=726`, and the connected component spans `x=-132..461`, `y=17..585`. They are clipped and unreachable.
- Admin audio playback is broken: the HTML appends `?auth=token`, but the route only accepts an `Authorization` header. Confirmed 401 vs 200.
- The admin dashboard renders note content and client-supplied capture IDs through `innerHTML`, creating stored XSS against the admin session.

## 4. P0 findings

### P0-1 — The app cannot be pointed at a backend, so the core voice pipeline fails on every real device

**Evidence**
- `mobile/lib/services/settings_service.dart:32-34` defaults `serverUrl` to `http://127.0.0.1:8000`.
- `mobile/lib/ui/screens/settings/settings_screen.dart:60-135` contains only three `SwitchListTile`s; there is no `TextField` for server URL or API key.
- `mobile/lib/main.dart:13-30` wires `SettingsService` directly; there is no onboarding or provisioning step.
- The only `serverUrl` setter is the property declaration itself; no UI or bootstrap code calls it.
- `mobile/lib/state/note_provider.dart:131-193` uploads voice notes only through that URL and marks them `failed` if health/upload fails.
- `mobile/lib/state/note_provider.dart:52-78` creates text notes, but `_syncNoteToBackend` only logs failures at `:97`.

**Impact**
- On a physical phone, voice capture always ends in `failed` after recording. The "Thought captured! Organizing…" snackbar is shown before backend success, so the user believes the note is being processed.
- Text notes work locally, but server graph and semantic recall never receive them.
- The client-side AI fallback cannot rescue this because `apiKey` also has no UI (`ai_service.dart:30`).
- Only developer workarounds (`adb reverse`, pre-seeded preferences, emulator-specific 10.0.2.2) make it work.

**Verification**
1. Install the release APK on a clean physical device.
2. Record a note.
3. Observe the snackbar, then open the note: status is `failed` with a connection error.
4. Open Settings: no server field exists.

**Fix recommendation**
- Add Connection settings for server URL and optional client token; validate and persist them.
- Provide a first-run setup screen or build-time `--dart-define` default suitable for the deployment.
- Add a "Test connection" action using `/api/health`.
- Do not show the success snackbar until the note reaches `ready` or is durably queued.

### P0-2 — Client API is unauthenticated; admin token is default; README exposes it on all interfaces

**Evidence**
- `server/app/api/routes/client.py:29` creates `APIRouter(prefix="/api")` with no dependencies. Upload, list, search, graph, relationship update, delete, eval record, and consent endpoints are all open.
- Destructive open endpoints include `DELETE /api/knowledge/{id}` (`client.py:209-213`) and `POST /api/eval/consent` (`client.py:279-286`), which calls `purge_unconsented()`.
- `server/app/api/dependencies.py:110-127` accepts a bearer token or `X-Admin-Token`; `server/app/infrastructure/config/__init__.py:15` defaults it to `echo-admin-secure-key-2026`.
- The same default is embedded in `server/app/static/index.html:305` and `:581`.
- `server/app/main.py:53-59` sets `allow_origins=["*"]` with `allow_credentials=True`.
- `README.md:109` instructs `uvicorn --host 0.0.0.0`.

**Impact**
- Any host that can reach the port can enumerate all knowledge, read transcripts, delete notes, upload data, and purge evaluation records.
- The admin dashboard is protected by a publicly known default token.
- Wildcard CORS with credentials is an unsafe combination and can enable cross-origin abuse from a browser if the service is exposed.

**Verification**
1. Start the server without `ECHO_ADMIN_TOKEN`.
2. From another machine, `curl http://<host>:8000/api/knowledge` returns data with no credentials.
3. `curl -X DELETE http://<host>:8000/api/knowledge/<id>` deletes without credentials.
4. `curl -X POST http://<host>:8000/api/eval/consent -H 'Content-Type: application/json' -d '{"consent_given":false}'` triggers the purge path.
5. `curl -H 'Authorization: Bearer echo-admin-secure-key-2026' http://<host>:8000/api/admin/status` succeeds.

**Fix recommendation**
- Add an auth dependency to the entire client router, using a per-install or per-user token issued during setup.
- Remove the default admin token; require `ECHO_ADMIN_TOKEN` at startup and fail closed if absent.
- Bind to `127.0.0.1` by default; make public binding an explicit opt-in.
- Replace wildcard CORS with an allowlist; do not combine `*` with credentials.
- Add tests asserting 401/403 for every client and admin route.

### P0-3 — Unauthenticated upload path traversal and unbounded memory read

**Evidence**
- `server/app/api/routes/client.py:47-50` reads the entire upload into memory and writes it to `os.path.join(upload_dir, f"{capture_id}.m4a")`.
- `capture_id` comes directly from a `Form(...)` field and is never validated as a UUID or sanitised.
- Confirmed with `TestClient`: uploading with `capture_id="../escaped"` and `consent_given=true` created `/tmp/opencode/trav2/escaped.m4a`, outside the configured upload directory.
- No request-size limit is configured in `client.py` or `main.py`.

**Impact**
- An unauthenticated attacker can write files outside the upload directory (limited to the `.m4a` suffix) and overwrite existing `.m4a` files.
- Large uploads are fully buffered in memory, enabling memory exhaustion/denial of service.
- Combined with P0-2, this is reachable by anyone on the network.

**Verification**
```bash
curl -X POST http://host:8000/api/captures/upload \
  -F 'capture_id=../escaped' -F 'idempotency_key=k' -F 'duration_ms=1000' \
  -F 'consent_given=true' -F 'file=@sample.m4a'
# then check for <upload_dir>/../escaped.m4a
```

**Fix recommendation**
- Validate `capture_id` as a UUID and reject anything else.
- Resolve the final path and assert it starts with the realpath of the upload directory.
- Stream the upload to a temporary file with a hard size limit; reject oversized requests with 413.
- Store metadata under a server-generated name, not a client-supplied one.

### P0-4 — Release artifact is debug-signed and still uses template identity

**Evidence**
- `mobile/android/app/build.gradle.kts:8,19` uses `com.example.mobile`.
- `mobile/android/app/build.gradle.kts:36` sets `signingConfig = signingConfigs.getByName("debug")` for release.
- `mobile/android/app/src/main/AndroidManifest.xml` uses `android:label="mobile"`.
- `mobile/pubspec.yaml:2-19` still says "A new Flutter project", version `1.0.0+1`.
- `flutter build apk --release` succeeds (~51 MB), but the artifact is not publishable.

**Impact**
- Google Play rejects debug-signed artifacts.
- Debug keys are not secret; the APK cannot be trusted as a production build.
- Users see the app as "mobile", not "Echo".

**Verification**
- `apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk` shows the Android debug certificate.
- Install and inspect the launcher label.
- Attempt a Play Console upload.

**Fix recommendation**
- Create a release keystore and signing config; keep secrets out of git.
- Set a real application ID (`com.<org>.echo`), app label, version, and description.
- Add a release checklist and CI check that rejects debug-signed release artifacts.

## 5. P1 findings

### P1-1 — Detail edit controllers go stale and overwrite AI results on Save

**Evidence**
- `mobile/lib/ui/screens/detail/note_detail_screen.dart:29-39` initialises `_titleController`, `_summaryController`, and `_originalController` once in `initState`.
- There is no `didUpdateWidget` or provider listener that refreshes controllers when the note changes.
- `:60-70` `_saveEdits` writes controller text back to the note.
- Confirmed by a temporary widget test: after the note updated asynchronously, entering edit mode and saving replaced the new AI title/summary with the old values.

**Impact**
- A user who opens a note while processing is still running can erase the AI-generated title and summary. This is silent data loss.

**Verification**
- Open a note in `pending`/`transcribing` state, wait for `ready`, then tap Edit → Save without changing text.
- The title and summary revert to the pre-AI values.
- Automated: add a widget test that inserts a note, pumps an updated provider value, enters edit mode, saves, and asserts the new AI values remain.

**Fix recommendation**
- Sync controllers in `didUpdateWidget` when the note's `updatedAt` changes and the user is not editing.
- If the user is editing, preserve their draft but do not overwrite non-edited fields on save.
- Disable Edit while the note is processing, or show a conflict prompt.
- Save only changed fields rather than reconstructing the whole note from controllers.

### P1-2 — Failed/queued notes are never resumed; success is reported before backend confirmation

**Evidence**
- `mobile/lib/state/note_provider.dart:105-125` inserts a `queued` note and calls `syncCaptureToBackend(note.id)` once, fire-and-forget.
- `:131-193` performs a single health check and upload. On failure it marks the note `failed` unless a client AI key is configured.
- `loadNotes()` (`:37-49`) only reads the database; it does not retry queued/uploading notes on startup or reconnect.
- `backend_service.dart:91-95` has a 3-second health timeout, but upload (`:102`) and semantic search (`:144`) have no timeout.
- `home_screen.dart:156-170` shows "Thought captured! Organizing…" immediately after local insertion.

**Impact**
- A killed app, transient network loss, or hung upload leaves notes permanently stuck.
- The user sees a success message for a note that never processes.
- There is no queue, backoff, or connectivity-triggered retry.

**Verification**
- Kill the server, record a note, restart the app with the server running: the note remains `failed`.
- Kill the server mid-upload: the note can remain `uploading` indefinitely because the HTTP request has no timeout.

**Fix recommendation**
- Implement a durable job queue with explicit states and `nextAttemptAt`.
- Resume `queued`/`uploading`/retryable `failed` notes on app start, foreground, and connectivity change.
- Add upload/search timeouts and exponential backoff with a max attempt count.
- Surface failure in the list with a Retry action; do not claim success before `ready`.

### P1-3 — Delete does not delete server capture, audio, jobs, or evaluation records

**Evidence**
- `mobile/lib/state/note_provider.dart:267-275` deletes the local note and calls `DELETE /api/knowledge/{id}`, swallowing all errors.
- `server/app/application/use_cases/__init__.py:267-268` `delete_knowledge` only calls `self.knowledge_repo.delete(item_id)`.
- `server/app/adapters/outbound/persistence/__init__.py:94-106` deletes the knowledge item, relationships, and embeddings, but not the capture or job rows.
- Retained audio is only removed inside processing (`use_cases/__init__.py:143-165`); there is no deletion hook.
- `mobile/lib/ui/screens/detail/widgets/delete_confirmation_dialog.dart` promises "This removes the audio, transcript, and organized ideas."

**Impact**
- The user is told the capture and audio are permanently deleted, but the server keeps them.
- Orphaned audio and capture metadata accumulate indefinitely.
- This is a privacy and data-lifecycle defect, not just cleanup.

**Verification**
- Upload a note with consent, delete it in the app.
- Check `server/uploads/` and the `captures`/`jobs` tables: the row and audio remain.
- Repeat with a note that failed and has `audio_path` set.

**Fix recommendation**
- Add a server-side "delete capture" use case that removes the knowledge item, capture row, jobs, evaluation rows, and any audio file, then updates storage metrics.
- Call it from delete with proper error handling; do not silently ignore failures.
- Keep the existing knowledge-only endpoint if needed, but make the mobile delete use the aggregate endpoint.
- Add an integration test asserting filesystem and DB cleanup.

### P1-4 — Consent withdrawal is not wired; retained audio cannot be purged from the app

**Evidence**
- The upload reads `evalConsent` at `note_provider.dart:150` and sends it per upload (`backend_service.dart:107-115`).
- `BackendService.updateConsent` (`backend_service.dart:163-170`) is never called anywhere.
- The Settings toggle only writes the preference (`settings_screen.dart:132-133`); it does not notify the server.
- `client.py:279-286` can purge evaluation records, but it is unauthenticated, and it does not delete capture audio.
- `use_cases/__init__.py:143-165` purges audio only during processing when consent is false.

**Impact**
- Turning consent off prevents future retention but does not purge audio already retained.
- The app cannot honour a withdrawal request.
- Combined with P0-2, an attacker can also trigger purge without authorization.

**Verification**
- Upload with consent on, toggle consent off, confirm the old audio remains in `server/uploads/`.
- Call `/api/eval/consent` with false and confirm audio is untouched.

**Fix recommendation**
- Call the consent endpoint when the toggle changes, with authenticated identity.
- Implement a server-side purge that removes audio for all captures when consent is withdrawn.
- Make the destructive consent endpoint authenticated and idempotent.
- Add tests for opt-in, opt-out, and purge.

### P1-5 — Local database upgrade drops every note

**Evidence**
- `mobile/lib/data/datasources/database_helper.dart:25-31`: `onUpgrade` executes `DROP TABLE IF EXISTS notes_fts` and `DROP TABLE IF EXISTS notes`, then recreates.

**Impact**
- Any future schema version bump wipes all local notes, including audio references and transcripts.
- This is latent today (version 2) but guaranteed to cause data loss on the next migration.

**Verification**
- Install version 1, create notes, bump the DB version, install version 2: notes disappear.

**Fix recommendation**
- Replace destructive upgrade with incremental migrations (`ALTER TABLE`, backfill, copy-and-swap).
- Add a migration test that seeds notes at each schema version and asserts preservation.

### P1-6 — Knowledge graph places nodes outside its fixed canvas and hides relation-load failures

**Evidence**
- `mobile/lib/ui/screens/library/widgets/knowledge_graph_widget.dart:258` fixes the graph height at `490`.
- `:280-288` wraps the graph in `SizedBox(width: 500, height: 500)`.
- `graph_layout_engine.dart:135-145` places circular clusters with `radius = max(110, count * 36)` around `center = (170, clusterY + radius)`.
- A temporary layout test found isolated nodes at `maxY = 726` and the connected component spanning `x = -132..461`, `y = 17..585`.
- `knowledge_graph_widget.dart:59-80` catches all relationship-load errors, sets the list to empty, and only changes the loading flag; no message is shown.

**Impact**
- Nodes outside the canvas are clipped and unreachable, so the graph does not represent the knowledge base.
- When the backend is down, the graph silently shows no relationships, which looks like data loss.

**Verification**
- Create 8+ isolated notes and a multi-node connected component; open Library → Graph.
- Observe clipped/missing nodes and no error banner with the backend stopped.
- Extend `mobile/test/graph_layout_test.dart` to assert all node bounds fall inside the viewport, not just non-overlap.

**Fix recommendation**
- Compute the bounding box of all positioned nodes, then scale/translate to fit the available viewport.
- Make the canvas match the actual available size rather than a hardcoded 500×500.
- Support pan/zoom for dense graphs.
- Show an explicit "Could not load relationships" state with Retry.

### P1-7 — Admin audio playback is broken by header-only authentication

**Evidence**
- `server/app/api/routes/admin.py:18-20` applies `verify_admin_auth` to the admin router.
- `server/app/api/dependencies.py:110-127` only reads the `Authorization` header or `X-Admin-Token`.
- `server/app/static/index.html:643` and `:703` build audio URLs as `${c.audio_url}?auth=${encodeURIComponent(token)}`.
- Confirmed with `TestClient`: `GET /api/admin/captures/cap1/audio?auth=<token>` returns **401**; the same request with `Authorization: Bearer <token>` returns **200**.

**Impact**
- The admin dashboard cannot play any retained audio, which is a core inspection feature.

**Verification**
- Open a capture with audio in the admin UI; the player fails silently/401.
- Reproduce with the two curl/TestClient requests above.

**Fix recommendation**
- Fetch the audio with the auth header, convert the response to a blob URL, and assign that to the `<audio>` element.
- Alternatively, issue a short-lived signed URL for audio playback.
- Do not put long-lived tokens in query strings or logs.

### P1-8 — Stored XSS in the admin dashboard

**Evidence**
- `server/app/static/index.html:640-667` interpolates `c.original_transcript`, `c.resolved_item.title`, concepts, and `c.error_message` into `tbody.innerHTML` without escaping.
- `:731-780` interpolates title, core idea, details, concepts, tags, open questions, provenance, and error messages into `resolvedContainer.innerHTML`.
- `:666` embeds `c.capture_id` directly into `onclick="openCaptureDetail('${c.capture_id}')"`; `:782` does the same for `retryJob`.
- `capture_id` is client-supplied on upload and is not sanitised (P0-3), so an attacker can inject markup through the ID itself.

**Impact**
- Since the client API is unauthenticated, an attacker can plant a payload in a note or capture ID.
- When an admin opens the dashboard, the payload executes in the admin origin and can read the token from `localStorage`, call admin APIs, or exfiltrate data.

**Verification**
- Upload a note whose transcript/title is `<img src=x onerror=alert(document.domain)>`.
- Open the admin dashboard and the capture detail; the payload executes.

**Fix recommendation**
- Build DOM nodes with `textContent`, or escape every interpolated value.
- Avoid inline `onclick`; attach listeners with `addEventListener` and data attributes.
- Add a strict Content-Security-Policy.
- Do not rely on the known default admin token.

### P1-9 — Missing iOS microphone usage description

**Evidence**
- `mobile/ios/Runner/Info.plist` contains no `NSMicrophoneUsageDescription`.
- The app records audio via `AudioService` and requests microphone permission.

**Impact**
- On iOS, the app terminates when it first accesses the microphone because the usage description is missing.

**Verification**

**Fix recommendation**

- Add a microphone permission integration test or at least a build-time plist assertion.

## 9. Confirmed vs potential vs unverified

### Confirmed defects

- Backend URL/API key cannot be configured; default is localhost (P0-1).
- Unauthenticated client API and known default admin token (P0-2).
- Upload path traversal and unbounded body read (P0-3).
- Debug-signed release and template identity (P0-4).
- Stale detail controllers overwrite AI output (P1-1, widget test).
- No retry/resume and premature success (P1-2, code path).
- Delete leaves server data/audio (P1-3, code + data inspection).
- Consent withdrawal not wired (P1-4).
- Destructive DB upgrade (P1-5).
- Graph nodes outside viewport (P1-6, layout test).
- Admin audio 401 (P1-7, runtime).
- Stored XSS in admin HTML (P1-8, code inspection).
- iOS microphone key missing (P1-9).
- Tab state reset and recording abandonment (P2-1/P2-2, widget/code).
- Nav overflow, contrast, search race, 500-vs-422, dead settings, copyWith null semantics, repo hygiene (P2).

### Potential risks

- Android release HTTP cleartext may fail on device. The manifest has no `usesCleartextTraffic`/network security config, and targetSdk is 36; Flutter's `dart:io` often bypasses Android's cleartext policy, so this is not asserted as a defect.
- Client-side AI key storage would expose the key on-device if a settings field is added; server-side proxying is safer.
- fastembed model download at first use can be slow or fail offline; startup backfill catches per-item errors but semantic search may 500 until the model is available.
- Unauthenticated eval consent purge can be triggered by anyone on the network.
- Admin XSS impact depends on whether the dashboard is exposed beyond localhost.

### Unverified areas

- Real device recording, permissions, 30 s cutoff, and STT quality.
- Real speech extraction quality with/without `OPENAI_API_KEY`.
- iOS build and runtime behavior.
- Android cleartext behavior in the release build.
- XSS payload execution in a real browser.
- Multi-user/concurrent load, long-running stability, and SQLite locking.
- Play Store signing/upload path.
- Accessibility with TalkBack/VoiceOver.

## 11. Acceptance criteria

A release candidate is acceptable only when all of the following are true:

1. A clean install on a physical Android device, configured only through the UI, can record a note and reach `ready` with title, summary, transcript, and concepts.
2. The app survives an app restart and a server outage: queued notes resume and failed notes expose a retry that succeeds.
3. Every client API request without a valid token returns 401; the default admin token is rejected; the server binds to localhost unless explicitly configured otherwise.
4. Uploading with a non-UUID `capture_id`, `../` segments, or a body above the limit is rejected; no file is written outside the upload directory.
5. Deleting a note removes the local row, server knowledge item, capture row, job rows, evaluation rows, and audio file; the confirmation copy is accurate.
6. Withdrawing consent prevents future retention and purges previously retained audio; the behavior is covered by an integration test.
7. Upgrading the local database from the previous schema preserves all notes and audio references.
8. Opening a note during processing and saving an edit never replaces newer AI title/summary values.
9. The graph shows every node inside the viewport at 1.0× and 1.5× text scale, with pan/zoom, and shows an error when relationships fail to load.
10. The admin dashboard plays retained audio successfully, and a note containing HTML/JS renders as text.
11. `flutter analyze`, `flutter test`, server tests, and the release build pass in CI; the release APK is production-signed and labelled Echo.
12. No P0 or P1 finding remains open.

## 12. Five highest-value next actions

1. **Make the app configurable and reachable.** Add server URL + token settings and a connection test; ship a default that works outside the developer machine. This unlocks every other end-to-end test.
2. **Close the security perimeter.** Authenticate the client API, remove the default admin token, bind to localhost by default, restrict CORS, and validate/confine uploads. This addresses P0-2 and P0-3 together.
3. **Implement the delete/consent lifecycle end-to-end.** Add a server-side capture-delete use case and a consent-withdrawal purge; make the UI copy truthful. This is the largest privacy gap.
4. **Eliminate data-loss races.** Fix detail controller synchronisation and replace destructive DB upgrades with migrations before any schema change ships.
5. **Add CI and regression tests for the confirmed bugs.** At minimum: stale edit save, tab state, graph bounds, upload validation, delete cleanup, admin audio auth, and XSS escaping. Without these, the same defects will return.

### Bottom line

Echo has a credible architecture and a working prototype pipeline, but it is not safe to ship. The first release should be treated as an engineering hardening release, not a feature release: configuration, authentication, upload safety, data deletion, and data-loss races must be fixed before any user data is placed on a shared server. The UI polish is ahead of the operational and security readiness.
